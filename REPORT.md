# Отчёт по выпускному проекту

**Название выбранного проекта:** Система знаний команды (поиск по своим данным + память)

## Ценность (для кого и зачем)

Продукт нужен командам, у которых знания разбросаны по документам, чатам и
головах отдельных сотрудников. Он даёт быстрый ответ на вопрос по
внутренним материалам и всегда показывает, на чём этот ответ основан
(источники), либо честно говорит «данных недостаточно» — вместо того,
чтобы придумывать правдоподобный, но неверный ответ.

Основные пользователи:
- новичок в команде — «где правила, ссылки, как у нас принято?»;
- менеджер/оператор — «как ответить клиенту в такой ситуации?»;
- руководитель/тимлид — «как сделать так, чтобы знания не жили только в
  голове одного человека?».

## 3 сценария пользователя

1. Пользователь загружает документ через раздел «Документы» → документ
   появляется в витрине, автоматически режется на фрагменты для поиска.
2. Пользователь задаёт вопрос в разделе «Вопросы» → получает ответ и
   список источников-цитат из конкретных документов.
3. Пользователь задаёт вопрос, на который в базе нет ответа (или уверенность
   модели низкая) → получает честный ответ «данных недостаточно», метку
   `needs_review=true` и причину, видимую в разделе «История».

## Точки доступа API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/kb/documents` | добавить документ в базу знаний, автоматическая нарезка на фрагменты |
| GET | `/kb/documents` | витрина документов для веб-панели |
| POST | `/kb/ask` | получить ответ по базе знаний со строгим JSON (источники или ручная проверка) |
| GET | `/kb/history` | история вопросов/ответов с фильтром «требует проверки» (для панели) |
| GET | `/kb/audit` | аудит всех запусков (для панели) |

## Схема данных (таблицы)

- **documents** (id, created_at, title, text) — исходные документы базы знаний
- **snippets** (id, created_at, document_id, snippet_text) — фрагменты,
  нарезанные по абзацам, единица поиска
- **qa_runs** (id, created_at, question, answer, sources_json, needs_review,
  error) — история вопросов и ответов
- **audit_runs** (id, created_at, action, input, output, status, error,
  duration_ms) — аудит каждого вызова каждой точки доступа

## ИИ-операция

**Схема JSON (строгий контракт ответа модели):**
```json
{
  "answer": "string",
  "confidence": 0.0-1.0,
  "sources": [{"snippet_id": "string", "quote": "string"}],
  "needs_review": true/false,
  "review_reason": "string|null"
}
```

**Температура:** 0.0 — детерминированный, без творческих вольностей в ответе
по внутренним документам.

**Когда включается ручная проверка:**
- подходящих фрагментов не найдено (запрос к модели даже не отправляется —
  сразу честный ответ «данных недостаточно»);
- модель вернула пустой или невалидный список источников
  (сервер отфильтровывает `snippet_id`, которых не было среди переданных
  фрагментов, — так исключается «галлюцинация источника»);
- уверенность модели ниже порога `CONFIDENCE_THRESHOLD` (по умолчанию 0.55);
- сбой при обращении к модели (сеть, невалидный JSON) — перехватывается,
  логируется в `audit_runs` со статусом `error`, пользователю всё равно
  возвращается безопасный ответ, а не ошибка 500.

Контракт `sources` пустой ⟺ `needs_review=true` проверяется на сервере
принудительно и не зависит от того, что «думает» сама модель — это и есть
основная защита от уверенных выдумок.

## Память/контекст

Что хранится: вся история вопросов и ответов в `qa_runs`, включая источники
и причину ручной проверки — видна в разделе «История» веб-панели с фильтром
по `needs_review`. Это и есть «память команды»: не только сами документы, но
и то, какие вопросы уже задавались и на какие из них система честно не
смогла ответить — готовый список тем, которые стоит дополнить в базе знаний.

## Контроль качества

**На входе:** ограничение длины заголовка и текста документа на уровне
Pydantic-схемы (защита от переполнения контекста модели), ограничение длины
вопроса.

**На выходе:** валидация структуры JSON от модели, фильтрация источников по
реально переданным `snippet_id`, принудительное согласование `sources` и
`needs_review`, перехват сбоев модели без падения сервиса.

**Поиск:** гибридный — BM25 по ключевым словам + векторный поиск (ChromaDB),
результаты объединяются по reciprocal rank fusion. При недоступности
векторного бэкенда система автоматически откатывается на поиск по
ключевым словам, не падая.

## План внедрения за 1 день

1. Поднять контейнер на внутреннем сервере (`docker compose up -d`).
2. Загрузить существующие документы команды (регламенты, FAQ, шаблоны ответов).
3. Дать команде доступ к веб-панели, показать раздел «История» — это
   готовая очередь тем для дополнения базы знаний.
4. Назначить ответственного, который раз в неделю просматривает
   «Требует проверки» и добавляет недостающие документы.

## Мини-экономика

- Ручной поиск ответа в разрозненных документах/чатах: ~15–30 минут на вопрос.
- Через систему: ~1–2 минуты (запрос + чтение ответа с источниками).
- На 100 вопросов в месяц: экономия ~20–45 часов рабочего времени команды
  против стоимости токенов LLM (для `gpt-4o-mini` — доли доллара на 100 запросов).
- Вывод: ценность растёт с размером команды и текучкой кадров — онбординг
  новичков перестаёт требовать постоянных вопросов «старожилам», а знания
  не теряются при уходе сотрудника.

## Риски и меры снижения

1. **Модель придумывает ответ без источника** → строгая серверная валидация:
   пустой `sources` принудительно даёт `needs_review=true` независимо от
   ответа модели.
2. **Векторный поиск недоступен** (нет сети/ключа) → автоматический откат
   на BM25-поиск, приложение не падает.
3. **Утечка секретов в репозиторий** → `.env` в `.gitignore`, в репозитории
   только `.env.example` без значений.
4. **Слишком длинный документ ломает контекст модели** → лимит длины текста
   документа на уровне схемы запроса.
5. **Модель возвращает невалидный JSON** → try/except, ошибка пишется в
   `audit_runs`, пользователю — честный ответ вместо падения сервиса.
6. **Ложные источники (несуществующий snippet_id)** → сервер отфильтровывает
   источники, которых не было среди переданных модели фрагментов.

## 3 строки для портфолио

- **Проблема:** знания команды разбросаны по документам и головах людей,
  ответы на одни и те же вопросы ищут заново каждую неделю.
- **Решение:** веб-система с гибридным поиском по базе знаний и строгим
  ИИ-ответом, который либо цитирует источник, либо честно признаёт
  нехватку данных.
- **Результат:** производственный прототип с полным аудитом, воспроизводимым
  Docker-запуском и 10 тестовыми сценариями, включая обязательную ручную
  проверку.

## Сложности и как решал(а)

- BM25 давал отрицательные оценки на маленьком тестовом корпусе документов
  (частые термины получают отрицательный IDF) — фильтрация по `score > 0`
  ошибочно отсекала релевантные фрагменты. Решение: ранжировать по
  относительному порядку без фильтра по знаку оценки, полагаясь на
  reciprocal rank fusion с векторным поиском.
- Инициализация BM25-индекса падала с `ZeroDivisionError` на полностью
  пустой базе знаний (свежий старт без документов). Решение: пропускать
  построение BM25-индекса, если фрагментов ещё нет, и полагаться на
  раннюю проверку «фрагментов не найдено → сразу needs_review» в `main.py`.

## План развития

- Права доступа и разделение базы знаний по командам/проектам.
- Уведомление ответственного при накоплении нескольких вопросов на одну
  тему в `needs_review` — сигнал, что нужен новый документ.
- Версионирование документов вместо перезаписи.
- Экспорт истории вопросов в CSV/JSON прямо из панели.
